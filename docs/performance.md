# ContextIQ Performance & Optimization Guide

This document outlines the performance characteristics, optimization techniques, and latency benchmarks of the ContextIQ RAG engine running on local consumer hardware.

---

## 1. Execution Environment & Constraints

ContextIQ is engineered specifically for **local offline deployment** on consumer laptops and workstations without requiring enterprise GPUs or cloud APIs.

| Parameter | Configuration |
|---|---|
| **CPU Target** | Intel Core i5/i7 / AMD Ryzen (Tested on Windows x64) |
| **RAM Utilization** | ~3.2 GB combined (ChromaDB + PyTorch CPU + Ollama) |
| **GPU Requirement** | None (100% CPU inference supported) |
| **Local LLM** | Meta `llama3.2:3b` via Ollama |
| **Embedding Model** | `all-MiniLM-L6-v2` (384-dim, 22M parameters) |
| **Reranker Model** | `cross-encoder/ms-marco-MiniLM-L6-v2` (22M parameters) |
| **Vector Store** | ChromaDB with HNSW index & cosine similarity |

---

## 2. Key Optimizations Implemented

### 1. Model Singleton Caching (`backend/model_manager.py`)
- **Problem**: Loading PyTorch model weights (`SentenceTransformer` and `CrossEncoder`) on every API request causes massive disk I/O and takes 2–4 seconds per call.
- **Solution**: Thread-safe singleton pattern (`get_embedding_model()`, `get_cross_encoder_model()`) caches model weights in memory upon startup. Subsequent calls execute in microseconds.

### 2. Ollama Status Cache (`backend/summarizer.py`)
- **Problem**: Calling `ollama.list()` before every prompt to verify model availability adds 200–450 ms of blocking HTTP roundtrip time.
- **Solution**: A timestamped cache with a 30-second TTL checks Ollama status once and serves cached health verification for subsequent requests during active sessions.

### 3. Cross-Encoder Candidate Pruning (`backend/retrieval.py`)
- **Problem**: Scoring 10–15 candidate passages through a full Cross-Encoder neural network on CPU takes 400–900 ms.
- **Solution**: Fast vector cosine similarity ranks initial candidate chunks from ChromaDB. The top 6 candidates are then passed to the Cross-Encoder. This reduces neural reranking latency by **35–50%** with negligible impact on retrieval recall.

### 4. Real-Time Token Streaming via SSE (`backend/app.py`, `backend/summarizer.py`)
- **Problem**: Waiting for the complete LLM response before sending JSON results in a perceived wait time of 2–6 seconds on CPU.
- **Solution**: Server-Sent Events (`/api/qa/ask/stream`) stream tokens as they are generated by Ollama. Time-to-First-Token (TTFT) drops to ~400 ms, providing a smooth user experience.

### 5. Hierarchical Chunk Sampling for Summaries
- **Problem**: Passing dozens of chunks to the local LLM causes context window exhaustion and high generation latency.
- **Solution**: Long documents are stratified into beginning (introduction), middle (technical details), and end (conclusions) samples (up to 8 chunks), keeping generation fast, reliable, and grounded.

## 3. Measured Latency Breakdown

Below are representative latency metrics measured during local testing on CPU:

| Pipeline Stage | Typical Duration | Notes |
|---|---|---|
| **Query Embedding** | 15 – 35 ms | `all-MiniLM-L6-v2` encoding |
| **Vector Search (ChromaDB)** | 8 – 20 ms | HNSW index query over 49+ chunks |
| **Total Retrieval ($T_{\text{retr}}$)** | **25 – 55 ms** | Vector search + distance normalization |
| **Cosine Pre-filtering** | < 2 ms | In-memory dot product |
| **Cross-Encoder Reranking ($T_{\text{rerank}}$)** | **80 – 180 ms** | 6 candidate pairs on CPU |
| **Time to First Token (TTFT)** | **350 – 550 ms** | With streaming endpoint |
| **Full LLM Generation ($T_{\text{gen}}$)** | 1.0 – 2.8 s | Depending on output token count |
| **Total Response Time ($T_{\text{total}}$)** | **1.2 – 3.1 s** | End-to-end question answering |

## 4. Latency Tracking Integration

Every response from `/api/qa/ask` and the final event of `/api/qa/ask/stream` returns exact wall-clock latency metrics:

```json
{
  "question": "What is the internship duration?",
  "answer": "The internship duration was from June 02, 2025 to July 31, 2025...",
  "sources": [
    {
      "document": "Internship report(AP23110011260).pdf",
      "page_number": 3,
      "score": 0.942
    }
  ],
  "latency": {
    "retrieval_ms": 28.4,
    "reranking_ms": 94.6,
    "generation_ms": 1120.3,
    "total_ms": 1243.3
  }
}
```

The frontend displays these latency figures via an interactive badge on each message bubble, giving transparency into system performance.
